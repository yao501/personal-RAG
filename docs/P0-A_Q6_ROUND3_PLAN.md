# P0-A / Q6 Round 3 — 可接受答案形态收敛（production-like checklist）

## 范围与约束（必须遵守）

- **只做**：把 Q6 的评测从“暴露缺口”推进到“**什么算可接受答案**”。
- **本轮只补**：2～3 个 Round 3 case（带 `acceptable_variants`）。
- **不做**：不改 5.3 closeout；不继续优化 Q8；不新增 retrieval/ranking/chunk/parse 规则；不切去做 P0-C；不重写 `answerQuestion` 主干。

## 1) 为什么 Round 3 现在比 P0-C 更优先

- Round 2 已把问题稳定钉在 **answer 层**，但当前评测仍偏“逐字硬约束”，容易把**语义等价、结构合格**的答案误判为 fail/partial。
- 在不动检索规则的前提下，Round 3 的价值是把“可接受生产回答形态”收敛成 checklist，避免后续修补时出现“修了但评测不认/评测认了但用户不认”的摇摆。

## 2) 本轮解决的不是 retrieval，而是 answer 验收标准过硬/过窄

Round 1/2 的信号说明：

- 工程总控 FAQ（如“先编译后下装”）容易被命中，但 **控制器侧要点**、**两阶段边界**、**guardrail** 不稳定。
- 评测应允许**同义表达**与**结构化表达**（分点/先后/分阶段），但仍要禁止“只答泛化 FAQ、完全不点控制器侧”的情况。

## 3) 什么叫“可接受答案形态”

针对 Q6，同一问句下答案满足以下之一可视为可接受：

- **控制器侧可接受表达**：明确点出“控制器/控制器算法工程”，并表达“先编译后下装”顺序（允许同义措辞、允许分句）。
- **两阶段分点结构可接受表达**：明确区分“控制器侧 vs 工程总控/站侧”，可用分点、分句或“先…再…”结构表达。
- **guardrail 可接受表达**：出现“不要混淆/先区分边界/不要把…写到…”等提醒，措辞允许变化，但必须能让用户避免把两阶段混写。

## 4) 什么仍然必须算 fail

- 完全不点“控制器/控制器算法工程”（只给泛化“先编译后下装”）。
- 出现反向错误（如“先下装后编译”）。
- 把控制器侧与工程总控侧混写成一个阶段（没有边界提示，且没有任何 guardrail）。

## 5) 验收方式（最小闭环）

- Round 3 通过 `acceptable_variants` 表达可接受的同义/结构形态。
- runner 规则：
  - `expected_shape` 满足 → pass
  - 若 `expected_shape` 不满足，但任一 `acceptable_variants[*]` 满足 → **pass（标注 accepted_by_variant）**
- 产物：照旧输出 raw/results/summary，确保可回归、可 review。
